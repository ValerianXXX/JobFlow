# Source, queue, and offline adapters

Start at the company HTTPS careers page. Derive its registrable domain; reject public suffixes such as `com` or `co.uk`. Navigation must begin at the exact verified official URL and end at exact `current_url`. Every hop is company domain/subdomain, an explicitly approved intermediary, or the final ATS tenant bound to company, host, tenant, board, job identity, official-page hash and JD hash.

Before real-site authorization, `discover-official-jobs` may inspect only a user-supplied project-local HTML or saved-page JSON snapshot. Treat page text and scripts as untrusted data; execute nothing and perform no network request. Keep only company-domain links or explicitly approved ATS hosts, deduplicate by provider/tenant/board/job identity, and never infer a missing title or location. Every result remains `NEEDS_LIVE_FRESHNESS_CHECK` and `requires_route_verification=true`; offline discovery is evidence for a future check, not proof that a vacancy is open.

Prefer guest. Missing guest flow becomes a user handoff; JobFlow neither creates an account nor reads credentials. Recheck official listing/form freshness before analysis, assisted prefill and any future user submit attempt.

Queue capacity is `AWAITING_APPROVAL + RESERVED <= pending_limit`, where the user limit is 1—1000. Reservation and capacity check use one immediate transaction. At capacity, intake remains `DEFERRED` and creates no Job, JD snapshot or Application. Older deferred intake has strict FIFO priority over a new arrival, and released capacity can reserve every available slot atomically. Content hashes make repeated intake idempotent.

Continuous intake is `MANUAL_TICK_ONLY`. A strict project-relative manifest may contain only local synthetic job inputs and opaque `secure-ref` values. `plan-continuous-intake` reports the queue-bound plan without processing it; `run-queue` requires an explicit invocation for every tick. Neither command registers a Windows task, Codex automation, background service, browser action or network action. Real or unattended job intake remains unauthorized.

Phase 5—6 define Official Source, Browser Prefill, Submission, Account Creation, Email, Recruiter, Scheduler and Receipt protocols. Most transports remain fake/mock/dry-run/disabled. The sole narrow real transport is the fixed-ID, loopback-paired Browser Companion for a separately approved, user-present application. It may inspect one bound provider origin, fill only approved fields, stream approved files with one-use tokens, and activate one unambiguous non-final Next/Continue control after form validation and a fresh one-use navigation authorization. Every new page receives a rotated action session and fresh classification. It never reads current values, cookies, tokens, passwords or page bodies, and cannot invoke final Submit. Fake scheduling uses an in-memory clock; no Windows task, Codex Automation, SMTP, email, recruiter action or background application service is registered.

The checked-in provider verticals remain synthetic evidence, not live-site certification. Greenhouse and Lever bind saved routes, tenant/job identity, snapshots, generated materials and review packets. Ashby and SmartRecruiters add saved provider-JSON discovery plus single-form synthetic browser evidence. Workday additionally proves a three-page local sequence with reusable fields, a manual-answer stop, login/CAPTCHA handoff, scoped forward navigation, later-page resume/Cover Letter/portfolio attachment, trusted user final Submit observation and verified synthetic receipt. No public recruiting site is accessed by those tests.

`ats-capabilities` remains the authoritative disclosure: `SYNTHETIC_VERTICAL_PASS`, `SAVED_SEQUENCE_PASS`, `SINGLE_SNAPSHOT_PASS` and `DIRECT_SNAPSHOT_PASS` describe checked-in evidence only. Every provider remains `live_site_verified=false`. Real use always needs a current approved route, one application-specific user-present authorization, compliance with site terms, and a user-owned final Submit.
