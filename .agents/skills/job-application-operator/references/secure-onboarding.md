# Secure onboarding

Real private data is imported only with dedicated commands and encrypted immediately by Windows DPAPI under `%LOCALAPPDATA%\JobOps\private`. Do not pass private values as command arguments. Candidate Profile, Answer Bank, master DOCX/PDF and Claim approvals receive opaque `secure-ref:*` identifiers.

The project database stores only reference ID, safe display kind, ciphertext/content hashes, version, state, synthetic flag and timestamps. Decryption occurs in memory or a restricted staging folder outside OneDrive. Staging is removed on success and failure. Revocation prevents further reads; user-confirmed deletion removes ciphertext and marks metadata deleted. Report deleted files and references, but never claim SSD secure erase.

Generated real DOCX/PDF, visual records and Review Packets use the same private store. Ordinary output may expose status, hash, version and secure reference, never plaintext. `purge-synthetic-private-data` removes all active synthetic ciphertext before release.

# Minimal real onboarding

When the user has authorized bounded Downloads discovery, `secure-onboard-resume` selects the best 2026-Aug DOCX or a PDF-only fallback, hashes and encrypts it, drafts the private Candidate Profile and Answer Bank, and proposes unapproved Claims against read-only evidence. It returns only a visual-session token and safe metadata. Inspect every rendered page at original resolution, then call `finalize-resume-onboarding --session <token> --page-result PASS` once per page. Use `review-onboarding --latest` for the redacted packet.

The onboarding stop is `AWAITING_USER_CLAIM_AND_PROFILE_APPROVAL`. A PDF-only result must retain `EDITABLE_MASTER_DOCX_MISSING`; it is a reference resume and cannot support layout-preserving editable tailoring.

# Local onboarding center

Run `onboarding-center` to open the private one-time setup UI on `127.0.0.1`. The page switches between Chinese and English without sending content to an external translation service. It collects three source families: applicant documents, AI-derived material, and 25 direct answers. Every draft update rotates encrypted DPAPI content; the public project index carries only references, counts and status. The home-page AI connection control may auto-detect a prepared Hermes/OpenClaw Agent or a model server on an explicit loopback endpoint on Windows or WSL. WSL discovery is bounded to registered distributions and allowlisted commands; distro names and executable paths stay ephemeral and are never persisted. Never extract, return or persist Agent credentials or browser sessions, and never place private material in a command argument. Windows and WSL local-model HTTP is restricted to loopback; WSL HTTP request bodies travel through stdin, never a WSL IP or LAN listener. For WSL Hermes, inspect only its public active model/provider selection and invoke that already-configured runtime through an isolated stdin/stdout adapter with an empty tool surface, one model turn, no session database, no memory, no context files, no checkpoints and a disposable working directory. Do not infer Hermes readiness from unrelated providers shown as signed out, and do not use raw ACP as the JobOps analysis bridge because its normal tool surface is broader than this contract. If the selected Hermes provider cannot complete a synthetic zero-tool handshake, fail with an actionable message rather than attempting login. Windows and WSL OpenClaw runs use a disposable empty workspace and a minimal analysis-only tool policy; filesystem, runtime, web, UI, automation, messaging, node, agent, media and plugin tools are denied. Hermes and OpenClaw results are accepted only when their tool-call audit reports exactly zero calls. Agent-routed data follows the Agent's own local/cloud model configuration and the UI must say so plainly.

Document uploads are preview-first and AI-required. A configured private AI engine must return a structurally valid, fully covered response after reconstructing wrapped lines and consolidating unique real-world entities. `work`, `internship`, `education` and `project` are distinct controlled types; responsibilities and achievements inherit the type and identity of their parent entity. Every accepted AI candidate remains unselected and requires confirmation. There is no deterministic Claim fallback: a fragment, title, unsupported number, weak citation, bad category or ambiguous entity relation is filtered individually and counted without retaining its wording. Such a candidate produces no Claim preview, but it does not reject an otherwise readable file. The user can confirm and securely retain a source even when zero candidates remain, and a valid DOCX can still become the editable master. Pending candidates stay inside encrypted onboarding state; only user-selected, editable statements become Claim candidates. Existing retained document sources can be reprocessed into a replacement preview. A one-click include-all action is still an explicit user selection and never external approval. Deleting an imported source requires explicit confirmation and removes its encrypted copy, suggestions, direct Claims and provenance-derived Claims. Claim review supports wording/category edits, delete/restore, same-entity merge and split while preserving provenance IDs; none of these operations set `approved_for_external=true`.

One model response may be nondeterministically malformed even when the source is valid. If the first response is structurally malformed, or all of its candidates are individually filtered, pass the numbered source and rejected response back to the same private AI exactly once as a replacement request, using the same stdin/memory-only and zero-tool boundary. Re-run the full validator on the replacement. Record only non-private repair and filter counts in the encrypted preview summary. If the replacement has a valid top-level protocol but still contains bad candidates, filter those candidates and keep the source; do not retry again. Return `AI_RESPONSE_REPAIR_FAILED` only when the replacement still lacks the required top-level protocol. Never auto-punctuate a Claim, widen provenance mechanically, invent facts, or fall back to rule splitting.

Pass private AI input through memory or local-process stdin, never command arguments. Expose a redacted engine status in the UI and do not reveal executable paths, credentials, prompts or private content in project files or logs. Treat malformed or failed AI output as unavailable and emit no Claim candidates. A conflict exists only when relevant sources compare the same normalized dimension and provide different values; identify that dimension and both values in plain language. Irrelevant or non-comparable mappings are suppressed as invalid mappings, never displayed as conflicts or raw knowledge blocks.

An official ChatGPT export is a special, explicitly user-authorized intake route, not a Knowledge Gateway source. Standard ZIPs of at most 200 MB are read in memory. Larger exports use the explicit streaming option: the browser transfers the selected file only to the loopback service, which hashes it while writing to a one-use restricted staging directory under `%LOCALAPPDATA%`, outside OneDrive. The streaming route is bounded to 8 GB, validates member count, compression ratio, encryption state and the single `conversations.json` member, incrementally parses the top-level array, and cleans staging on success or failure. Only applicant-authored message content is considered; export attachments, logs, assistant output and browser/account data are never indexed. Secret-like fragments are excluded, candidate suggestions remain `AI_DERIVED_REQUIRES_CONFIRMATION`, derived metadata is encrypted, and the raw ZIP is never retained. The original selected file is read-only and is not moved, renamed, overwritten or deleted.

The UI must label the >200 MB route clearly in both languages. File transfer progress uses measured loopback throughput. After transfer, parsing and AI analysis show an honest model-dependent time range and elapsed time; a passed estimate must switch to a long-running state and must never restart or replenish a countdown.

`ONBOARDING_COMPLETE` requires all questions resolved, continuity-critical eligibility fields explicitly answered, Profile confirmation, every Claim confirmed or rejected, and all detected conflicts resolved. Background check, non-compete, truth attestation and electronic signature policies stay `confirm_each_application`; UI completion never authorizes a real external action.

Completion is an immutable version boundary. Every mutating onboarding endpoint fails closed on a completed state. `Start revision` creates a new encrypted onboarding state and Answer Bank with a pointer to the previous state; it never rotates a completed Profile, Answer Bank, approval packet or completion packet. The operation is idempotent: when the newest state is already editable it returns that same revision without another write, so a stale page can safely synchronize after retry. Changed Claims return to review and completion gates run again.

For individually supplied files, the older dedicated imports remain available:

1. Secure-import Candidate Profile JSON.
2. Secure-import Answer Bank JSON.
3. Secure-import editable master resume DOCX; a PDF may be retained but cannot preserve editable layout by itself.
4. Propose Claims from read-only `personal_redacted` evidence, then have the user approve each wording, responsibility boundary, allowed use and expiry.
5. Check `secure-store-status`; do not inspect plaintext through ordinary CLI.
